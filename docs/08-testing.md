# 08 · 测试

## 1. 现在的自动化闸门（提交前必过）

| 命令 | 时间 | 抓什么 |
| --- | --- | --- |
| `devecocli check arkts --fix` | 秒级 | 绝大多数 ArkTS 类型/语法错误，比全量构建快得多。**每轮改完跑一次即可，不要每个 edit 跑** |
| `devecocli check lint` | 秒级 | 代码规约，规则档位见 `code-linter.json5` |
| `devecocli build` | 分钟级 | 真链接：资源引用、`$media:`/`$string:` 缺失在这里才暴露 |
| `python tools/qp-gate/selftest.py` | 秒级 | 网关侧 70 项，见 §3 |
| `python tools/doc_line_check.py` | 秒级 | 两件事。① 文档里指向代码的那些"文件.ets + 行号"还指得动吗：越界、落在空行、或句子点名的符号在那一行附近已经找不到；顺手查 markdown 相对链接指向的文件还在不在。② 每个 `Copy.fill*` 调用点的占位符数量和它填的那条模板对不对得上（见下面那段） |

ArkTS 比 TS 严：`any`/`unknown` 不允许，对象字面量要有形状，`struct` 的字段初始化是强制的。
`--fix` 能补 `export` 这类高置信度问题，补不了的先看它报的行号。

文档里指向代码的行号是对读者最有用的部分，也是最容易悄悄坏掉的部分：代码只要往上挪三行，
引用就变成"已经核对过"的假证据。`tools/doc_line_check.py` 扫 `docs/` 下全部十一篇，加上
`QwenPawMobile/` 根目录的 `README.md` / `CHANGELOG.md` / `CONTRIBUTING.md` / `SECURITY.md`
（本地那份 `AGENTS.md` 也在扫描范围内，它不出问题，所以总数不受它进不进仓库影响；
条数**以命令自己打印的那一行为准**，这里不写死 —— 这一篇也是被它扫的），
它只证明**那一行附近还写着句子里点名的那个符号**，不证明句子本身说得对 ——
后者仍然要靠读代码的人。

链接只查"方括号写文字、圆括号写相对路径"的那种 markdown 链接：反引号里的路径**故意不查**。
那些反引号里写的经常不是仓库里的文件，而是构建产物（`entry-default-unsigned.hap`）、
设备上跑出来才有的路径（`cacheDir/media/…`）、用户主目录里的桌面端配置，或者句子里的举例
（`某文件.ets`）—— 一次扫下来 340 个候选里 29 个"查不到"，全部是这几类，把它们报成问题只会
让闸门变成噪音。所以这里明写边界：**断链=有闸门，路径引用=没有**。

`doc_line_check.py` 的第二趟管的是文案的**占位符**：全 App 的用户文案集中在 `l10n/Copy.ets`，
填它们靠 `fill` / `fill2` / `fillN` / `fillN2` / `fillNums` 这几个形状各异的函数，而
`String.replace('%s', …)` **只换第一个** —— 于是模板里多写一个 `%s`、或调用点少填一个参数，屏幕上
就是一行光秃秃的 `%s`，ArkTS 检查与 lint 都不会报。这一趟把每个调用点和它点名的常量配对，比对数量。
第一次跑（本轮）：**0 个不匹配**，只有一条被列成"注意、不算失败"：`pages/HomePage.ets:136` 是
`fillN(fill2(home_group_count, …), n)`，外层填的模板是另一趟刚拼出来的字符串，占位符数量在这里
**算不出来**，所以它只提醒人看一眼（那条模板是 `%s %s · %d`，两层刚好分完）。

它拦的方向也有边界，并且是**试过才知道的**："某条常量带着占位符、却没有任何 `fill*` 去填"这一类
**故意不查**。第一轮把它写进去了，报出来两条：`Copy.chat_part_file`（`[文件: %s]`，它被
`state/ChatStore.ets:48` 存进 `PartTemplates.fileTemplate`，由 `Parts.label()` 在别处填）和上面那条
嵌套的 `home_group_count`。静态分不出"由另一层填"和"忘了填"，留着就是每轮两条噪音 —— 与"反引号里的
路径不进闸门"同一条理由，所以这一条边界也写在 §1 里。
**它确实拦得住**：临时把 `home_row_meta` 从 `%s · %s` 改成 `%s · %s · %s`，那一处 `fill2` 调用点
（`ui/home/SessionRow.ets:103`）立刻被报"模板三个、只填两个"，闸门 exit 1；改回去重新 0 problems。

**这五条目前是"人跑的"，不是"机器拦的"**：移动端这一侧没有 CI workflow（桌面端仓库自己的
workflow 不算在这里——它们构建的是桌面版）——要在 CI 上跑就得在
runner 里装 DevEco Studio + API 20 SDK 并解决许可与签名，公开 runner 上并不划算。
所以"提交前必过"目前是**约定**，不是保障；谁提 PR 谁自己跑，review 时先看有没有跑过的证据。

## 2. 端到端没有自动化，所以必须写清"测的是谁"

UI 侧目前是**人工 + 脚本驱动设备**回归，没有 UI 自动化用例。汇报或提 PR 时请标明：

- 连的是**真实桌面端**还是桩/mock。**mock 通过不算联调通过**——
  真实端才会暴露帧序、鉴权与上传上限这些差异。
- 设备与形态（真机型号 / 模拟器形态 + 断点桶），见 [06](06-responsive-devices.md)。
- 走没走 qp-gate（走了意味着测的是网关 + 后端两层）。

那个"桩"跟着**桌面端那一棵树**走（`scratch/mock-qwenpaw.js`），**不在移动端仓库里**：
只克隆了移动端仓库的人手上没有这个文件，要演这套场景得把那份桩单独带过来。
下面两条命令是在放着桩的那棵树里跑的。

```bash
node scratch/mock-qwenpaw.js --port 8088           # 默认只绑 127.0.0.1
node scratch/mock-qwenpaw.js --host 0.0.0.0        # 只在模拟器要经 10.0.2.2 连它时
```

它照 v2.2.2-beta.4 的 console 契约做：`/api` 前缀、bearer 鉴权、按 object 分辨的 SSE 帧、
`replay_end`、生成中 409、审批、上传，以及 ＋ 菜单要的 `/api/skills` 与 `/api/mcp*`
（**非 GET 一律 405**，用来证明手机真的没往桌面端写配置）。场景靠发送的文本触发，按
`userText.includes()` 依次判定：`限流` / `图片` / `视频` / `语音` / `本机路径` /
`发文件`（电脑端把文件交出来那一条，六份文件、六种 mime：两份走 `base64` 内联，其中一份
**连 `name` 都不带**，照真实历史里那个形状）/
`孤儿卡`（只有 call、没有 output，用来造长度 1 的工具段）/ `工具`（十张卡）/ `审批` /
`失败` / `表格` / `长`（慢流）/ `断流`。另有三个开关式的启动参数：`--replay-real`、
`--long-names`、`--running-pair`。默认账号是脚本里写死的
`demo` / `qwenpaw`（`--auth 0` 可以演"桌面端没开鉴权"这个分支）。这份桩的凭据是公开的，
`--host 0.0.0.0` 又让同网段任何设备都能连上它，所以用完当场停掉，别让它挂在局域网里过夜。

## 3. qp-gate 自检

```bash
python tools/qp-gate/selftest.py
```

自带桩上游，不依赖桌面端，也不碰你真实的 `~/.qwenpaw`。等价的入口是
`tools\qp-gate\start.bat check`（同一条 selftest，另外 `start.bat discover` 只打印
探测到的上游端口后就退出，可用来确认网关找没找到桌面端）。覆盖：鉴权面接管与不泄漏、
口令错误/限流、伪造与过期令牌、无令牌转发、`Connection` 头改写、X-Forwarded-For、SSE 分帧到达时间、
8MB 请求体字节一致、二进制逐字节一致、畸形请求与 `CONNECT` 隧道拒绝、
网段白名单、上游发现（乱协议端口不能把发现流程炸掉）、地址展示（横幅与 `--show` 打的
必须是手机真能填的局域网地址，不能是 `0.0.0.0`）、`--edit` 的问答路径（一路回车等于
什么都没改、改端口不重生成 `token_secret`、演练用的临时配置不去动系统防火墙）、
防火墙放行的**回读确认**（拉起提权进程不等于放行成功）、`log()` 在 stdout 已关时绝不抛。
**改完 `qp_gate.py` 必跑**，它是纯 Python 标准库，不需要 pip install。

## 4. 想加单元测试从这里入手

`oh-package.json5` 声明了 `@ohos/hypium` / `@ohos/hamock`（devDependencies），
仓库里目前**没有**用例文件。架构本身是为可测设计的：

- `StoreHub` 构造函数接收 `Transport`（`state/StoreHub.ets:1-8`），
  所以可以拿假 transport 构建 `AppStore`/`ChatStore` 并断言状态，**不需要设备**。
- `StreamReducer` 是纯函数式归并（帧进、事实出），最适合做表驱动用例：
  delta/非 delta 覆盖、心跳不可见、终态判定、工具调用与输出配对。
- `Failure` 的状态码映射、`Breakpoint` 的阈值分桶同理。

优先级建议：`StreamReducer`（历史 bug 都在这）> `Failure` > `Prefs` 归一化。

    以及 `打开 ›` 的视频/文件两路在真机上交给系统后的落地（§7）。
15. 输入框上方**自占一行**的工具带：A/T 切文字与语音两态（A=audio、T=text），旁边是 ＋
    与（有草稿时才出现的）×；三个 selector chip 在它们下面另起一行，**不许被挤成省略号**。
    语音态下整条输入栏换成「按住 说话」—— 按住开始录、松手把**这一段单独发出去**
    （不动草稿、不动托盘里别的东西）、手指上滑越过阈值文案变「松开取消」且松手即丢弃；
    语音态下发送键让位，只有托盘非空时才回来；录音中 T 必须是**无效的**（收起说话条
    会让人找不到停止键），停止/丢弃仍走录音条那两个按钮和 ＋ 菜单里那对开关。文字态里
    打了一半再切去语音、切回来，草稿一个字不少。语音态下长按气泡「引用这段文字」或用
    「📝 长文本」，都要**自动回到文字态**并把内容显示出来，不能让内容落进一个看不见的
    框里、只留下一个亮起来的发送键。
16. ＋ 菜单里两个新面孔。**技能**：菜单里只有**一行**「🧩 技能 (电脑)」，点开是一张
    只读列表面板（`ui/chat/SkillPanel.ets`）。列表内容只有电脑端已启用、且渠道含
    `console`/`all`（或压根没写渠道）的才出现；停用的、只给别的渠道的，一行都不许漏出来。
    每行左边 `emoji + 名字`、右边那条 `/名字`、下面最多两行简介，简介长就被省略号截掉，
    但行高一致、整行可点。面板自己封顶可滚（真机上是 18 条，一屏放不下）。点一行**关掉
    面板**、只把 `/名字` 写进输入框，**不自动发送**；发出去之后桌面端真的按那个技能跑，
    只有真实端能判。一个技能都没有时 ＋ 菜单是**灰掉的**「电脑端没有可用的技能」，
    点它没有任何反应（菜单不关、输入框不动）。**MCP**：`🔌 MCP (电脑)` 打开只读清单，
    每行右侧是 transport，停用的那个是「已停用」；
    展开能看见工具及其启用状态，停用的客户端显式写「客户端已停用，读不到工具」而不是空列表。
    面板上一句「只读：手机上不能开关客户端，也不能改它的工具」要在。全程
    `url`/`headers`/`env`/`args` 里的凭据**一个字都不许**出现在屏幕、日志或崩溃文件里。
17. 工具带那三个图标**常驻**：A/T、＋、×。× 在空字段时是灰的、点下去没反应也不关任何东西；
    一旦字段里有字（打字、从技能面板点出来、引用带进文字）它就变成**红**（`app_error`），
    点一下清空文字、红回灰，附件托盘**不受影响**。红只给字形，不给药丸底 —— 整块红会被读成报错。
18. `💭 深度思考` 这一块**跟着这一轮走**：流式过程中展开（右边写 `▴ 收起`），这一轮的正文
    一开始就自己折叠成只剩标题行（右边 `▾ 看想法`），正文一个字都不露；点标题行能重新展开，
    再点收回。重进一个老会话，思考块应当是**折叠**的 —— 历史里的想法不该占掉回复的位置。
    折叠只改渲染，转录与发给服务端的字节都不动。
19. 文件气泡是**两行的卡片**，不是内容预览：`📄 文件名`（路径只显示最后一段，电脑端给的是整条
    Windows 路径时也不能把前半截显示出来）+ 第二行 `MD 文件 · 本机 12.3 KB` 或 `MD 文件 ·
    仅电脑端`，右边跟一个 `查看 ›`。点卡片要**先取字节**（那一行换成 `正在取字节…`，`查看 ›`
    消失，此时连点第二下**不许**起第二个 fetch），随后**系统自己拦一道**「"QwenPaw"想要打开
    "<某个应用>"」（`取消` / `允许`，app 不能代点），点`允许`才把交接交出去；阅读器里看到的
    应当是那份文件的**正文**。没有应用能读它时给一句 `这台手机上没有能打开它的已装应用`，
    卡片不留在忙碌态。长按同一张卡片仍然是 `引用这个文件`（长手势与点击互不抢）。
    这一条只加"看"，**不加删**：删除副本依旧只在资产面板和清理页。
20. 工具卡（`🔧 recall_history{…}` 那种，含 `· 输出` 的变体）是**两行折叠卡**，不是内容预览：
    默认只有标题行，右边写 `▾ 看详情`；点标题行展开内容、提示变 `▴ 收起`，再点收起复原。
    展开的内容不设行数上限（读进来时已经裁过，展开就该看到它真正持有的那点东西）。
    工具卡一次到齐（归并器从不把它标成流式中），所以只有这一个开关，没有第 18 条思考块
    那对"流式 / 已结束"的状态要覆盖；两者互不干扰。
    **连着两张以上还会先并成一组**：默认收起，只见一行组头 `🔧 工具卡 ×N ▾ 看详情`；
    点组头展开出组里的单张卡（各自还能再开详情），组头提示变 `▴ 收起`，再点收起复原。
    只有一张时不并组，就是上面说的普通单卡（桩里发 `孤儿卡` 可以造出这个形状：
    call 到了、output 没来）。组与单卡都是**视图层**的合分，转录与发给服务端的字节都不动。
    **但卡片只要带着文件就不进组**，并且把它所在的连排打断成两段（`🔧 工具卡 ×2` +
    一张带文件的卡 + `🔧 工具卡 ×3`）。理由和合组相反：合组是为"一排什么都没交付"的
    卡省屏幕，而这张卡刚刚把一份文件交到这台手机上，把它折进 `×N` 等于把交付藏起来。
    文件行画在卡片正文**上方**（图/影/音/文档各按第 16–19 条的形状），正文换成那句
    工具自己说的话；`output` 不是块列表的普通卡照旧整段显示，一个字符都不改写。
    **带着文档的那张卡，标题行写的就是那个文件名**（`📁 测试1.txt`，主色加粗），工具自己的
    名字挪到标题下面一行照旧显示 —— 一排 `🔧 send_file_to_user` 是扫不出来的，而滚屏幕要的
    正是那个名字。只带图/影/音的卡没有文件名可写，标题照旧是 `🔧 工具名`（媒体本身就是标记；
    真机 + 真实端在一轮里同时发过 png / wav / mp4，三张卡各带一行媒体、都不进组，见 §6 末）。
    **交付那几行的颜色与折卡分开**：文档行是主色底 + 主色描边 + 加粗主色文件名，语音行加主色
    描边（填充仍然只标"正在播放"这一件事，不给同一个控件掺第二个状态信号）；用户自己发出去的
    那一份保持灰底细边 —— 一眼分得清"交到这台手机上的"和"我发出去的"。
21. 主页的 `主题 ▾` 打开**三选一菜单**：跟随系统 / 浅色 / 深色，当前模式带 `✓`。点一条
    立即生效（浅色 ↔ 深色的底色、文字一起换），再打开菜单 `✓` 已跟着走，选回「跟随系统」
    随系统回到原样。以前的"按一下换下一个"循环不再存在 —— 循环要想到达想要的模式得先
    猜顺序，菜单一眼看全。
22. **电脑端把文件发过来**（桩里发 `发文件`）：那一轮的六张 `send_file_to_user · 输出` 卡
    每张**上方**长出一行文件 —— 图直接解码、clip 带播控、语音成音频卡、三份文档各一张
    两行卡片；卡片正文不再是那整段 JSON，而是工具自己那句话；普通工具卡（`命中 3 条结果`
    那种）正文**一个字符都不许多**。顶栏 `📁` 只数取得到的那份（内联的 `data:` 按既有规矩
    不进面板）。工具没给名字的那一份内联块**不显示 base64 尾巴**，屏幕上是一行「内嵌文件」，
    大小写本机折算出来的字节数，且**不给 `查看 ›`**（字节已经在消息里，没有可取的引用）。
    退出会话再进来，上述全部照旧 —— 直播流与历史共用同一个解析函数，两边不
    许各说各话。资产面板列得出这几份，`打开` 把字节取进缓存再交给系统阅读器。

### 真机 + 真实桌面端：重连横幅撤不掉（2026-10-05 深夜，nova 14 Pro，**非 mock**）

上面那条"第三次探测就没了"的结论在同晚被推翻，起因是收工前又看了一次手机。

- **现象**：手机连得上、主页每 10 秒轮询都在成功转发（网关日志里能看到那条来自手机的
  `GET /api/chats`），聊天页却仍挂着 `'连接中断（Operation timeout），2 秒后自动重连…'`。
- **根因**：这条文案是 `ChatStore.onRetrying()` 往转录里 push 的一条 NOTICE，而
  **没有任何代码在连接恢复后撤销它**；history 重建又**故意**保留 NOTICE
  （`state/ChatStore.ets:588` 那段注释：不能让"已停止"/"生成失败"被重建吃掉）。
  所以它只在离开并重回聊天页（store 随页面重建）时才消失 —— 之前那次"自愈"就是这么来的，
  不是倒计时走完了。附带一条：每次重试都再 push 一句，退避越久叠越多。
- **复现**（这条比"跑完之后残留"更强，走的是流中途断）：发一条要写满十句话的问题 →
  `● 生成中` 时把网关进程停掉 → 顶栏气泡变 `'连接中断（Failed to receive data from the
  peer），2 秒后自动重连…'` → 再把网关起回来。
- **修法**：给这条通知一个可撤销的调性 `NoticeTone.RETRYING`，加 `retireRetrying()`，在
  三个"等待已经结束"的点上撤：`open()`（流重新打开，含重连与用户新发一条）、`resync()` 里
  "历史加载成功但对端已经不在跑"那一支（这条路径不会再 `open()`，正是残留的那一支）、
  `giveUp()`（"重连失败"是这件事的最后一句，不该和一句过期的承诺同时挂在屏上）。
  ERROR / MUTED 两种调性一个字都不动 —— "你停止了"和"生成失败"是真发生过的事实。
- **结果**：重连那一刻横幅消失，`● 生成中` 继续跑到完成，整屏读不到任何"中断/重连"字样，
  也不再叠重复条。真机 + 真实端验过。
- `check arkts` 63 文件 0 错、`check lint` 0 错 12 条警告（名单与上一轮相同，没新增）、
  `run` 装机冒烟 PASS。

### 超长引用改发一份文本附件：模拟器 + mock（2026-10-06 早，nova 14 Pro，**测的是桩**）

  留下的残骸还得另立一套删除规则，和 #127 的条目级删除撞语义；`pending` 本来就不落盘，
  内存里这份和它同生命周期，不需要多一个要清的东西。
- **阈值仍按字**（`QUOTE_MAX = 600`）：输入框装的是字，按字节定的话同一条中文消息在
  手机上会比在电脑端早三倍截断，而这三倍没有任何一端能解释。
- **可发现性**：预览切在**行边界**上。第一版切在 600 字处，屏上最后一行是
  `11. 方舟运行时`，读起来像渲染器断了，不像"引用还有下文"；补一行

### 一句 `as T[]` 能把进程杀掉：列表形状守卫（2026-10-06，nova 14 Pro，**测的是桩**）

`JSON.parse(raw) as T[]` 在 ArkTS 里是**断言不是检查**：编译期过了，运行期也不看。所以只要服务端
在某个列表端点上回一个 200 的 JSON 对象（不是数组），第一次 `for...of` 取迭代器就抛
`TypeError: obj is not Callable`，而这个抛点在 `GlobalPoller.tick()` 的 10s 定时器里 —— 未捕获异常
到 ArkUI 的 AppKit 那里就是**整个应用没了**，不是"这一页坏了"。

修法是把"这里要的是列表"这件事写成一次真检查：`api/Shape.ets` 的 `expectList<T>(value, what)`
不是数组就抛 `Failure.parse`（屏幕上是一句中文 + 端点名），是数组才交出去。哪些入口过它、哪些**故意**
不过，判据写在 CHANGELOG：调用方已经有 `try` 的两处不重复包，读对象的（`history()`）不属这一类。

验证靠桩的一个开关：`node scratch/mock-qwenpaw.js --chats-object 1` 让 `/api/chats` 回
`200 {"note":"poisoned"}`。看到的应当是**没有崩溃**：同一个 PID 活着，`devecocli log` 里每 10s 一句

```
轮询失败：/chats 返回的不是一份列表
```

首页仍是上一次的好快照 + 一条「无法连接服务器」横幅。**把桩恢复干净再跑一次**（不带那个开关）：
登录、按渠道分组的会话列表、点进会话全部照常 —— 这一半才是这条改动的回归，光看"不崩"看不出
守卫把正常响应也挡了。

顺带说明为什么 `GlobalPoller` 的 catch 里多了一行 `Log.warn`：横幅只有一句通用的"连不上服务器"，
而"服务器连上了、答的东西不对"是**相反**的情形，没有这一行日志，两种故障在屏幕上长得一模一样。

同类写法全量扫过一遍（27 个 `JSON.parse` 调用点），结论是**没有第二处能把进程杀掉**：列表入口都进了
守卫；嵌套列表那两处（`ComposerApi.commands()`、`AgentApi.listForChat()`）的抛点在 async 函数体内，
调用方各自接住 —— `loadCommands()`（`pages/ChatPage.ets:221`）用 `.catch`、
`refreshAgents()`（`state/AppStore.ets:304`）用 `try`，最坏是一句灰掉的空清单；
`normalize()`（`model/Providers.ets:37`）把缺数组的字段补成空列表，所以下游 `for...of` 拿到的一定是
数组；`feed()`（`stream/StreamReducer.ets:79`）本来就在 `try` 里，坏帧直接丢。**下次再读到一处
`JSON.parse(x) as T[]` 就直接按这一节判**：要么过守卫，要么当场说清谁接住它。

### 发送与 SSE 的 409 / 429 分支：模拟器 + mock（2026-10-06，nova 14 Pro，**测的是桩**）

上面那句"仍未验证"欠的是**同一条状态码在另一条路径上的另一支**：登录页拿 `403` 说的是「登录失败」，
发送路径拿 `403` 走的是 `handleFailed()` 的"服务器已判定、重连只会重复"那一支。要一条一条走到屏幕上，
唯一的办法是让桩**按顺序**答复 `POST /api/console/chat`：`GET /__fail?codes=409` 装填一次，下一次发送
就被拒一次，日志里 `!! injected 409 (reconnect=false)` 是"这一支真的被请起来了"的凭据。

**先说一条走不到的支**：`handleClosed()` 里 `status === 409 && !isReconnect` 想接的是"另一个客户端正在
这个会话里生成"。真机上不用注入就撞不到它 —— `GlobalPoller` 每 10s 一次 `probe(chatRunning)`，只要服务端
报 running，手机就会在**用户点发送之前**把那条运行收养过来（`attach()`），于是根本没有一次带正文的 POST
发出去。这条不是 bug（收养比让手机吃 409 更对），但它意味着**"自然的 409"在手机上近乎不可达**，
只有注入状态码能把那一段代码摆到屏幕上。

跑完看到的三件事：

| 注入 | 屏幕上 | 桩的日志 |
| --- | --- | --- |
| `409` | 气泡留下来了，标「未送达」，一条「这条没有发到服务器…」 | 紧跟一次 `parts: []` 的 reconnect POST，然后 `GET /api/chats/chat-005` 重建 |
| `429` | 同上；退避那行「N 秒后重连」在 resync 成功后自己消失 | 只消费 `429`，队列里剩下的 `500, 503` **一个都没被碰到** |
| 清空 | 流式回复照旧，**没有**多出「未送达」 | 正常一帧一帧吐 |

第二行那个"剩下的没被消费"是**修法本身决定的**，不是漏跑：`429` 落进 `isTransient()` → `scheduleReconnect()`
→ `resync()`，而 resync 读的是**历史**、不是重发那条 POST。所以一次被答复的拒绝永远不会自己变成第二次
POST —— 这也正是"文字无声消失"那个 bug 的成因，见 CHANGELOG。

同一轮还顺手把**长按引用**在标了「未送达」的气泡上过了一遍：长按 → 「引用这段文字」→ 输入框里是
`> 未送达测试429`。提示条那句话不是空承诺。

**最后一段要的是"服务器连一次答复都不给"**，而桩给不出这个形状 —— `GET /__fail?codes=` 只是让它
**答复得难看**，仍然是一次答复。要让 `Failure.httpStatus === 0`，只有把桩进程直接杀掉这一种办法。
于是这一趟不是注入状态码，而是：**杀掉桩 → 立刻发一条 → 只截图，不点任何东西**，看着 2/4/8 那三级
自己走完。跑出来先暴露的是一个**只有看屏幕才看得见的缺陷**：屏上同时挂着三行
`连接中断（…），2 秒后自动重连…`、`…，4 秒后…`、`…，8 秒后…`，读起来像三次等待在排队，而事实是
只有最后那一级还没到期。原因是梯子的下一级从 `resync()` 的 catch 里直接再进 `scheduleReconnect()`，
**这条路不经过** `open()`，而撤掉等待行的 `retireRetrying()` 当时只挂在 `open()` 上。改完再走一遍同样的
步骤，每级恰好一行（在 `2 秒` 与 `8 秒` 各截了一次），走到头三句一起撤，只剩：

```
重连行只留一行          ← 我发的那条，标着「未送达」
这条没有发到服务器，长按它可以引用重发
重连失败。后台仍在生成时会自动继续探测，稍后可看到最新内容
```

再把桩放回来，不用退出重进：10s 那一轮询把会话状态探回 idle，发送键自己从「停止」回到「发送」，
下一发的流式回复照旧。**这一段同时补上了 `giveUp()` → STALE 在发送路径上的那一半**（之前只写过"未验证"）。

**这一节全部是模拟器 + mock**，真实端一条没测：409 需要另一个客户端抢着开流（真机上要做就是电脑端
和手机同时发），429 需要限流真的触发。留到 §7。

### 用户贴到 issue 里的那段日志会带上什么（2026-10-06，Pura X Max 模拟器 + **mock**，**动了代码**）

issue 模板和 `docs/09` §7 都让用户贴 `devecocli log --level W` 的片段，所以"那段里有什么"是要查的。
分两条，一条查完是好消息、一条查完改了代码。

**① 传输错误会不会把服务器地址带进日志 —— 不会。** app 自己那几行打的是 `Failure.message`，
而 `Failure.from()` 把 `@kit.NetworkKit` 的 `BusinessError.message` 原样透传，所以答案在系统那一侧。
把桩进程直接杀掉、让轮询连着失败几轮，模拟器上跑出来的是：

```

GET /chats dropped mid-read (transport=-2), retrying once
```

`Operation timeout` 是系统错误码表里的固定短句（`devecocli docs read
API参考/网络/Network_Kit_网络服务/错误码/HTTP错误码/errorcode-net-http` 那张表逐条都是这种不带宾语的
句子：`Failed to connect to the server.`、`Failed to resolve the host name.`），主机、端口、URL 都不在

**这一条不立，所以没动代码。**

**② 媒体引用会不会把电脑侧的绝对路径带进日志 —— 会，已改掉。** `media/` 里三行 `Log.warn` 打的是
`${ref}`，而真实端回给手机的那条 ref 正是电脑那台机器的裸绝对路径（`C:\Users\<用户名>\…\media\x.jpg` ——
`model/Parts.ets` 的注释把这一种写成"能用的那一种"，与取不到的 `file:///…` 相对）。三行现在改打缓存文件名，
也就是清理页和 `本机副本未能删除` / `缓存文件未能删除` 那几行**早就在用**的标识（FNV 散列 + 容器后缀）：

```
[Media] 缓存写入失败 131771f5.m4a: Operation timeout
```

同一串在改之前是 `[Media] 缓存写入失败 /mock/media/voice.m4a: …`（桩里的形状），换成真实端就是那条带
用户名的路径。改完仍然指得回同一个资产：散列就是那份字节落盘时用的文件名，用户按清理页那一行也能对上。

`10.0.*.**`，**真机是否同样打码未验证** —— 所以模板里"请删掉里面的真实 IP"那一句留着，不因为 ① 就把

### 后台会话条 + 「幻影运行中」的退避：三形态一轮（2026-10-06，**全是模拟器 + mock**，动了代码）

三台各走一遍同一套动作：nova 14 Pro（`sm`，API 20）、MatePad20（`lg`，API 20）、
Pura X Max（内屏 `lg`，API 26 Beta2）。装机都是 `devecocli run --apply`，三次 `Smoke: PASS`。
桩以 `--running-pair` 起：chat-002（飞书 · 项目群）与 chat-004（带附件的会话）标成 `running`，
但**没有对应的 RUNS** —— 这是故意造的"幻影运行中"，桌面端产生不了这种状态，它用来压客户端在
"历史说在跑、attach 却找不到活运行"时到底会做什么（改之前那件事就是下面的 274 req/s）。

**一、后台会话条**（`ChatPage.ets`）：打开一个与那两个都无关的会话（影音会话），条子出现并自己降数。

| 设备 | 条子 | 展开后的 chip |
| --- | --- | --- |
| nova 14 Pro | `⏳ 2 个后台会话进行中` [40,281,397,321] | 飞书 · 项目群 [40,343,401,395] / 带附件的会话 [414,343,774,395] |
| MatePad20 | [515,194,795,226] | [515,241,792,281] / [801,241,1077,281] |
| Pura X Max | `⏳ 1 个后台会话进行中` [357,230,648,263] | 带附件的会话 [357,280,650,323] |

点 chip 走 `pushUrl` 进那个会话（nova 上点了"飞书 · 项目群"、Pura 上点了"带附件的会话"），
返回键回到原来这个；被点到的幻影随即落回 idle，条子从 2 变 1（nova 回到影音会话时
`⏳ 1 个后台会话进行中` + 只剩另一颗 chip）、最后消失，主页角标同步。
Pura 上打开时已经是 1 而不是 2：那台更早的一次 attach 已经把其中一个幻影收走了（整台合计 2 个 POST）。

**主页与聊天页的数字不一致是设计，不是 bug**：主页角标（`AppStore.backgroundRunning()`）排除的是
**主会话**，聊天页条子排除的是**当前正看的**会话。主会话自己就在那两个跑着的会话里时，同一时刻
主页报 1、聊天页报 2 都对 —— 主页那张主会话卡自带「⏳ 进行中」chip（nova 的 dump 里
`▶ 主会话` + `⏳ 进行中` + 标题"飞书 · 项目群"三块都在）。

一个顺带看到的小性子：**进会话页不会触发一次轮询**（只有主页 `poke()`），所以条子要等下一次 10 秒
tick 的快照才出现 —— 进页面那一刻的 dump 里还没有，几秒后的同一页就有了。

**二、「幻影运行中」的退避**（`RunController.handleClosed()`）：改造前 nova 上这条路径是
**274 req/s** 的紧环（每次附带一个历史 `GET /api/chats/<id>`，合计 ~548 req/s），两分多钟之后
app 已经不在前台（复查时停在系统桌面、之后没有任何请求；没查到崩溃日志，挂起还是被回收没有定论）。
改后三台一致：

- 桩日志次序：`GET /api/chats/<id>`（历史）→ `POST /api/console/chat`（`reconnect:true`、`parts: []`）
  → **2 秒** → `GET /api/chats/<id>` → 之后回到 10 秒一次的心跳轮询；
- 14 秒窗口里**只有 1 个 POST**（改前 ~274/s；三台合计：nova 1、MatePad20 1、Pura 2）；
- 桩那侧幻影落回 idle 并盖上 `last_finished_at`：chat-002 @11:11:51.272Z（nova）、
  chat-002 @11:16:34.044Z（MatePad20）、chat-004 @11:17:56.231Z（Pura）；
- 界面上：条子降数、没有残留的"生成中"，输入栏回到空闲。

**三、桩的保真修补**（都是为了让它只说桌面会说的话）：`chat()` 现在带 `last_finished_at: null`
（桌面那个字段是 Optional，Pydantic 不排除未设置的可选值，键一定在）；`closeRun()` 结束时盖戳；
"重连但没有可重放的运行"这一支改成**一个立刻结束的空流**（桌面 `console.py` 的
`_empty_sse_response` 就是这个形状，不会只发一个 `replay_end` 就收线），并把那个幻影落回 idle。
前两条同时暴露了客户端一个真 bug：`null.length` 在 `onPoll()` 里抛，而它是静默的 —— 后台会话条
此前**一次都没显示出来过**，修法与桌面契约证据记在 CHANGELOG。

**四、窄屏 + 最大字号下的行内控件截断**（桩加 `--long-names`，用 MateX20 折叠态 1080px = `sm` +
系统字号拉满来复现）：两处同一病因 —— `Row` 不换行，长文本占满整行之后，下一个控件被量到窗口边缘
之外：会话页后台条的第二颗 chip 只剩 24px（`带附件的会话（这也是一条很长的标题） 查看 ›`
x=[1056,1080]）；主页更重，「🔒 N 项待审批」整颗不见（那是这一页通向待审批的唯一入口），
同状态 dump 里一行都没有。两处 `Row` 改成会换行的 `Flex` 后同机复测：两颗 chip 各占一行、整行可点
（[37,387,1031,463] / [37,469,1031,545]，点第二颗真的跳进了"带附件的会话"）、审批 chip 回到屏幕上
且可点（[75,661,421,725]）。短名对照在 nova 14 Pro 标准字号：仍是**一行**、「⏳ 1 个会话进行中」
照旧贴内容右缘（[882,449,1170,489]）—— 换行只在装不下时发生。截图与 dump 在 gitignored 的
`scratch/tmp/multi2/`（`m14-strip-crushed.png` 是改前那一张）。

**五、MatePad20 上的老坑**（上一节记过一次，这次又踩）：登录配置页**先 dump 再点**（键盘会把行挪走），

`hdc -t <serial> shell uinput -K -d 2 -u 2` 发一次 BACK 把它露出来。

**一、分组规则与实现位置（§5 第 20 条）**

组是渲染时现算的：`rows()` 把 `items` 切成"单行 / 连续 TOOL 段"，段 key 取首条消息的 key，
段长 1 走原单卡路径、段长 ≥2 画组头。转录、store、发给服务端的字节一律不动——服务端历史与
直播流汇进同一个 store 后形状相同，重进会话时同一段会按同一规则再分一次，组不必持久化。
展开出的成员卡就是第 20 条的普通单卡（同一个 `bubbleRow`），还能各自再开详情。

**二、键修复：直播流里组头为什么最初不出现**

第一版上线后，历史重进（整个列表重建）组头显示正常，但**直播回合里工具段从 1 张长到 10 张，
组头一直不出现**，停在单卡形态；回合结束也不变。根因是列表外层用的非惰性 `ForEach`：键值
不变的条目会**复用旧子树、不再执行 itemGenerator**。段 key 一直是首条的 key，段从 1 长到 10 时
没有任何东西让 ArkUI 重跑生成器。同理能解释"文字却一直在流"：气泡内容走 `@ObjectLink` 就地
刷新，而 `if/else` 分支、嵌套 `ForEach` 属于结构，键不变就不重新求值。修复是键函数并入成员数：
`row.key + '#' + row.items.length`，段每长一张键就换一次。

定位过程两个坑，记下省下次时间：① 所有「工具」回合渲染完长得一模一样，截图分不出新旧，
最后靠发一条带独特标记的「工具二」才把直播回合认出来；② hilog 的 NETSTACK 只记 GET 的完成行，
**streaming POST 没有 `method:POST` 行**——"日志里看不到发送"不能当判据，要看桩的服务端历史
（`GET /api/chats/<id>`）。

### 无名内联块把 base64 尾巴当成了文件名（2026-10-07 凌晨，**Pura 90 Pro 模拟器 + mock**，动了代码）

上一条那一轮收尾时按"系统性复查"又扫了一遍真实端的历史（只读 GET，不写任何配置），量出
`name` 这个字段的真相：两个真实会话 21 个 `data` 块里 **8 个没有 `name`**，其中 6 个是 `url`

**一、这一处 bug 是看屏幕看出来的，线级自测给不出**

桩的自测只看块列表的**形状**（能不能 parse、几份、mime 对不对），而形状全对时屏幕上依然可以
是一串乱码：内联块的 `ref` 是整条 `data:…;base64,…`，`Parts.leafOf()` 从它尾巴上切下来的那段
base64 就直接当了文件名。这正是 §2 那条规矩的另一头 —— 解析层对了不等于屏幕上对了，所以本节
每一轮都要走一遍 `devecocli ui`。同一个入口还连着暴露出两处不诚实：同一行第二格按缓存查大小，
内联块永远查不到于是写「仅电脑端」（可字节明明随消息到了本机）；第三格那个「查看 ›」在模拟器上
一点就红一句「没能取回 … 的字节」。

**二、三处修与一次接线漏**

取名三路（`model/Parts.ets:239`）、`Parts.inlineBytes()`（`model/Parts.ets:381`）按 base64 长度
折算字节、`Bubble.openable()`（`ui/chat/Bubble.ets:118`）对 `data:` 不给「查看」（与 `quotable()`
拒绝把 `data:` 编进请求体是同一条规矩）。**首版装机就翻在接线上**：`PartTemplates.inlineFile`
加了字段、`Copy.chat_file_inline` 加了词，却没在 `ChatStore.partTemplates()`（`state/ChatStore.ets:44`）
里赋值，于是屏上那行读成「文件暂不可用 / 未知类型 · 仅电脑端」—— 文案注入链断一环，闸门全绿
而屏幕是空的。接上之后是「内嵌文件 / 未知类型 · 本机 56 B」，无「查看」。

**没有**顺路做"把内联负载写进沙箱缓存、于是也能打开"：那需要一张 mime→容器后缀的表，而真实端
那份内联块是什么文件、有没有第二次被要过，都还没在真机上看清（AGENTS.md：不为没发生过的分支
写防御）。现在屏幕上那一行只说它说得出的话：有这份东西、多少字节、这台手机读不了它。

**三、桩跟着改形状**

`name`"的判据随之作废，换成一条**反向**判据：恰有一个块没有 `name`，且它的 `source` 是
`base64` + `application/octet-stream` —— 夹具要是哪天又把名字补齐，这一条会红，而屏幕上那串
乱码就是这么回来的。selftest **46/46**。

工具名，而电脑端明明给了 `test_audio.wav` / `test_video.mp4`（顶栏 `📁` 面板那几行读得到）。
原因是解析层把 `f.name` 只写进文档那一个槽位（`stream/StreamReducer.ets:292`、
`state/ChatStore.ets:693` 两处同形），图 / 影 / 音三个槽只留 ref。不能就地复用 `fileName`
顶上去：`Bubble.fileBlock` 的判据是 `fileRef.length > 0 || fileName.length > 0`，那样会在图片
下面多画一张文档卡。要补就得给三种媒体各加一个名字字段（`UiMessage` + 偏好持久化 + 两个解析点
+ 渲染），是一次独立的改动。危害比文档卡小得多：媒体行本身就是认出"这是那一份"的东西。
**这一条 2026-10-07 由使用者定为保持现状**（理由见 [05](05-architecture.md) 交付那一节），
下面 §7 里不因此新增条目 —— 现状已经在这块屏上实拍过，翻案才需要重拍。
